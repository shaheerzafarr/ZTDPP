ZTDPP Comprehensive Architecture & Engineering Report

This document serves as a complete, end-to-end technical breakdown of the Zero Trust Digital Provenance Platform (ZTDPP). It details every engineering decision, architectural workflow, and mathematical model used to build the platform from inception to its current state.

--------------------------------------------------------------------------------

1. The Core Philosophy: Zero-Trust Fusion

The fundamental problem with modern deepfake detection is that AI alone is not enough. Generative models (like Midjourney v6 or DALL-E 3) are improving so rapidly that they frequently fool standalone AI detectors. Conversely, Cryptography alone is brittle; if an authentic image is uploaded to a social media site that strips EXIF metadata, the signature is lost, and the image appears untrusted.

ZTDPP solves this via a Multi-Modal Fusion Architecture:
Trust(M) = 0.6 * Crypto + 0.4 * AI

- Cryptographic Provenance (60% weight): Provides hard, mathematical proof of origin. If a camera sensor signs the image, we know exactly where it came from. It is weighted heavier because cryptography provides deterministic truth.
- AI Inference (40% weight): Acts as a probabilistic safety net. If an attacker somehow steals a camera's private key and signs a deepfake, the AI will catch the synthetic artifacts and drag the total score down, preventing it from reaching the VERIFIED threshold.

--------------------------------------------------------------------------------

2. Artificial Intelligence Engine

Why EfficientNet-B4?
We evaluated multiple Convolutional Neural Networks (ResNet50, VGG16, MobileNet) before selecting EfficientNet-B4.
- Compound Scaling: EfficientNet uniformly scales depth, width, and resolution. This allows it to capture both macro-features (weird anatomy) and microscopic high-frequency artifacts (blending errors from GANs/Diffusion models).
- Performance vs. Compute: B4 achieves State-of-the-Art accuracy while having only ~19 million parameters. This allows inference to run on standard CPUs in under 500 milliseconds, crucial for our sub-2-second API latency requirement.

How the Model was Trained (Two-Phase Transfer Learning)
Training from scratch requires millions of images. Instead, we used Transfer Learning starting with ImageNet weights.
1. Phase 1 (Frozen Backbone): We froze the entire EfficientNet feature extractor. We replaced the final layer with a custom binary classification head (Dropout 0.4 -> Linear out=1). We trained this head for 5 epochs so it could learn to map pre-existing visual features to FAKE/REAL labels without destroying the pretrained weights.
2. Phase 2 (Fine-Tuning): We unfroze the deepest convolutional blocks (features.7 and features.8). We trained for 10 more epochs with a much lower learning rate (1e-5). This allowed the deep layers to adapt specifically to recognizing generative AI artifacts (like checkerboard patterns from upsampling).

Why CIFAKE?
For Phase 1 of the project, we used the CIFAKE dataset (120,000 images, 32x32 pixels, containing Stable Diffusion v1.4 fakes and CIFAR-10 real images). 
- The "Why": CIFAKE is lightweight and perfectly balanced. It allowed us to rapidly build the training pipeline, verify our loss functions (BCEWithLogitsLoss), and integrate the model into the backend without waiting days for training. 
- The Limitation: Because CIFAKE images are tiny (32x32), feeding the model high-resolution 4K real-world photos causes a "Distribution Shift." The model panics because it has never seen that level of detail, leading to extreme logit values.

Why ArtiFact for Fine-Tuning (Phase 2)?
The generative AI arms race is moving past Stable Diffusion v1.4. To make ZTDPP production-ready, it MUST be fine-tuned on the ArtiFact dataset.
- ArtiFact contains 2.5 million images.
- It features fakes generated by 25 different distinct architectures (GANs, Latent Diffusion, Autoregressive models).
- Fine-tuning on ArtiFact forces the EfficientNet to learn generalized synthetic noise patterns rather than memorizing the quirks of just one generator.

The Temperature Scaling Fix
To patch the CIFAKE distribution shift during our current testing, we implemented Temperature Scaling in the backend (ai_inferencer.py). 
By dividing the raw output (logit) by a temperature constant (T=4.0), we soften extreme predictions (e.g., changing a -49,000 logit to a manageable number before applying the sigmoid function). We also clamp the final AI score between 0.05 and 0.95. This mathematically prevents the AI from being "100% stubbornly confident" on out-of-distribution high-res images, ensuring it never totally overrides the cryptographic signature.

3. Cryptographic Signer & HSM Simulator

Real-world implementation of ZTDPP requires camera manufacturers (Sony, Canon, Apple) to embed a Hardware Security Module (HSM) directly onto the camera sensor. 

Because we cannot physically modify hardware, we built signer.py as our HSM Simulator.
1. Key Generation: Generates an ECDSA P-256 asymmetric key pair. The private key remains securely on the "device" (the signer folder), while the public key is registered in our backend SQLite database.
2. Hashing: Extracts the raw pixel bytes from the image and computes a deterministic SHA-256 hash.
3. Signing: Signs the pixel hash using the Private Key.
4. Manifest Injection: Packages the Device ID, Signature, and Hash into a JSON manifest and injects it directly into the image's EXIF metadata (UserComment for JPEGs, tEXt chunk for PNGs).

4. Backend Workflow (FastAPI)

The backend is built in Python/FastAPI for its asynchronous event loop, allowing high-throughput concurrent processing.

The /verify Endpoint Pipeline
When a user uploads an image:
1. File Validation: Checks MIME types and enforces a 10MB size limit, saving the file temporarily using asynchronous file I/O (aiofiles).
2. Parallel Dispatch: This is a critical performance optimization. Instead of running Crypto and AI sequentially (which would take ~1.5 seconds), the backend uses asyncio.gather() and run_in_executor(). It runs the Cryptographic check and the AI Inference simultaneously on separate CPU threads. 
3. Crypto Verification Step: 
   - Extracts the EXIF manifest.
   - Re-hashes the image pixels. If a single pixel was altered in Photoshop, the new hash won't match the manifest, and it fails.
   - Looks up the device_id in the SQLite database to retrieve the public key.
   - Cryptographically verifies the ECDSA signature.
4. AI Inference Step:
   - The image is passed to ai_inferencer.py.
   - The PyTorch model is loaded lazily (cached in memory on the first request to save startup time).
   - The image is resized using high-quality LANCZOS interpolation to 224x224.
   - The model outputs a probability score (calibrated via Temperature Scaling).
5. Aggregation: Both results are fed into the compute_trust() function (the 60/40 formula), generating the final JSON response.

The /sign Endpoint
Added to allow the React frontend to utilize the HSM simulator. It receives an image, runs signer.py in an isolated sub-process using the virtual environment (venv/Scripts/python.exe), and returns the signed file as a downloadable Blob.

--------------------------------------------------------------------------------

5. Frontend Workflow (React + Vite)

The frontend is a Single Page Application (SPA) designed with a premium, zero-trust aesthetic using Tailwind CSS. 

State Management & Routing
Instead of complex routing libraries, App.jsx maintains an appMode state to toggle between the Verification Engine and the HSM Signer.

Verification Engine Workflow
1. Upload Phase: Users drag-and-drop an image.
2. Analysis Phase: A sleek loading sequence triggers while the axios/fetch call is made to the backend.
3. Results Rendering: 
   - VERIFIED (Score > 0.8): Rendered with Emerald Green accents, shield checkmarks, and the image is displayed in full resolution.
   - UNVERIFIED (Score 0.4 - 0.8): Rendered with Amber accents. This usually happens if the AI detects anomalies in a cryptographically signed image, or if an authentic unsigned image is analyzed.
   - BLOCKED (Score < 0.4): Rendered with Crimson Red accents. Crucially, the image has a CSS blur-lg filter applied and pointer events are disabled. This enforces the "Zero Trust" concept at the UI layer—preventing users from accidentally viewing or saving a highly toxic deepfake.
4. Breakdown Cards: Displays the exact mathematical split (e.g., Crypto contributed 60%, AI contributed 32% -> Total 92%).

HSM Signer Workflow
Users input a device_id (like CAM-001) and upload a raw image. The frontend calls the /sign backend API. When the response arrives, the frontend creates a temporary window.URL.createObjectURL(blob), mounts a hidden <a> tag, and programmatically clicks it to force the browser to download the _signed image instantly.
